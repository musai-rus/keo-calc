Проект: **keo-calc** — веб-калькулятор проверочного расчёта КЕО по СП 367.1325800.2025, СП 52.13330.2016, СП 23-102-2003. Автор — Руслан (GitHub `musai-rus`).

1. Прочитай **`INSTRUCTION.md`** (инструкция проекта): методика, принятые решения, контрольные расчёты, журнал, бэклог, эксперименты. Это главный документ; этот файл — только правила работы.
2. В инструкции проекта два статуса:
   - **«Принятые решения»** (разд. 4–7) — менять только по запросу автора;
   - **«Эксперименты»** (разд. 12) — пробовать свободно; удачное переносится в решения после согласия автора.
3. Термины (не смешивать): **инструкция проекта** — `INSTRUCTION.md`; **инструкция проекта чата** — правила ИИ-агента (раньше — инструкции проекта Claude «99_КЕО», теперь — этот файл).
4. Перед работой над **«КЕО для Revit»** дополнительно прочитай [`TASKS.md`](TASKS.md) и **целиком** [`tasks/KEO_REVIT.md`](tasks/KEO_REVIT.md). Последний файл — единственное актуальное ТЗ Revit, GitHub Issue #13 — трекер выполнения, Slack — обсуждения.

## Отдельное направление «КЕО для Revit»

- Основной ближайший путь — **Dynamo/Python через Revit API → только нужные калькулятору входы → существующее JS-ядро → цвета Rooms и марки** (ТЗ v0.3.5). C#-срез сохранён как отложенный вариант; его подпись/загрузка не блокирует начало Dynamo. Не обходить блокировку DLL через Dynamo и не менять защиту Windows ради теста.
- Ветка экспериментального инструмента — `feature/revit-keo-prototype`; до отдельного согласования не включать его в `main` и не затрагивать Viewer/рабочий калькулятор. Документация общего реестра может быть объединена в `main` только с разрешения автора.
- Расчётное ядро (`engine.js`, `data.js`, `model.js`) остаётся **единым и неизменным**. Revit извлекает и подтверждает исходные данные, выдаёт совместимый JSON, визуализирует статус, но не реализует независимую формулу КЕО. Сложные геометрические алгоритмы в Python допустимы; портирование расчётных формул ядра в Python/Dynamo — нет.
- Состав извлечения определяет выбранная схема текущего калькулятора: [карта полей](revit-keo/INPUTS.md). Проверенные параметры, необходимые измерения и явный ввод с основанием допустимы. Не делать полный разбор тел/материалов обязательным условием расчёта; не привязывать рабочий код к номерам Rooms, ID, семействам, этажам и путям тестовой модели. Нехватка нужного входа даёт причину серого статуса этого Room, остальные продолжаются.
- Работу строить по этапам D0–D6 и подзадачам из ТЗ. Каждая задача: ссылка на требование, зависимости, проверяемый результат, статус, доказательство. Продолжать существующие Issue #13 и PR #15; не создавать повторные задачи/PR. Пока PR не объединён, читать ТЗ из рабочей feature-ветки. Текущий этап брать из Issue и ТЗ; не переносить старый статус из предыдущего отчёта.
- При любом согласованном изменении требований обнови `tasks/KEO_REVIT.md` (соответствующий пункт и датированный журнал) **в том же PR**, затем синхронизируй Issue #13. Не веди самостоятельное ТЗ в Slack или Issue. Изменения согласованных автором принципов — только с его отдельного одобрения.
- Результат синтетического теста/сборки не равен запуску в Revit или нормативной приёмке. Только подтверждённые используемые входы, применимость схемы и норма допускают зелёный/красный; остальные состояния серые с конкретной причиной.
- Исходный RVT не менять. При тестировании в Revit повторно использовать уже подготовленную standalone копию; не создавать новую на каждый запуск. Проверять активный документ/экземпляр, IsModified до/после и неизменность файла. Любые записи параметров/видов — отдельный этап после проверки цели, предпросмотра и разрешения автора на запись; D0–D4 только читают модель. Стадии, связи, единицы, север и UID фиксировать; недостоверные данные не заменять нулями.

- Перед геометрическим сбором определить нормативное назначение: подтверждённая норма → нужные поля выбранной схемы; подтверждённое отсутствие нормы → EXCLUDED/серый «КЕО не нормируется» со ссылкой на строку; неизвестное назначение → PENDING. Отсутствие строки в оцифрованном справочнике само по себе не означает отсутствие нормы. Не назначать переговорной норму рабочего кабинета только по принадлежности к административному блоку. Функция рабочего места, включая специальное оборудование, может требовать иной строки; неоднозначность сохранять явно.
- Текущая Revit-модель является источником состава и геометрии помещений. Невыпущенный обновлённый АР2 не является зависимостью расчёта. АР2/АР3 проекта используются для проверки подхода подрядчика, схемы и происхождения коэффициентов; старые размеры, номера, результаты и переход на СО автоматически не переносятся. Во время тестов по каждому выбранному назначению проверять нормы в сети и по экземплярам на Google Диске, фиксируя документ, редакцию, пункт/строку и дату проверки. Это проверка при разработке; пользовательский runtime остаётся локальным.

- Проектный расчёт не требует выбранной марки стеклопакета, паспорта изделия или оптических свойств Revit-материала. Использовать нормативные таблицы/формулы для явно выбранной расчётной категории и допустимые нормативные значения при неизвестных характеристиках; остальные принятые проектные допущения подписывать с основанием. АР3 — проверяемый ориентир, а не безусловный источник истины. Различать предписанное нормой значение, выбор строки/диапазона и проектное допущение. Отсутствие данных производителя само по себе не блокирует расчёт, но произвольное число не становится нормативным.

**Параметры условных семейств:** расчётный смысл параметра, единицу и область экземпляр/тип проверять до использования. Сопоставление задаётся настройкой проекта (GUID/ID либо однозначное имя), без встроенных названий семейств и проектных значений. Верхний и нижний проёмы независимы; радиус явно переводится в диаметр, если поле калькулятора требует диаметр. При подтверждённом автором условном представлении фонаря декоративные расширения, скругления и наружный габарит стекла не заменяют проектный размер светового отверстия. Расхождение сохранять в evidence вместе с решением автора; это не универсальное разрешение игнорировать реальные препятствия. При отсутствии/неоднозначности параметра — необходимый обмер или явный ввод с основанием; автоматическая догадка запрещена. Переносимость проверяется на другой модели, а не одинаковыми именами параметров.

## Окружение

- Для **веб-калькулятора** зависимостей нет: Node.js ≥ 18 (проверено на 22) и Python 3 (проверено на 3.13), только стандартные библиотеки. `npm install` не нужен. Dynamo-прототип требует проверки фактических версий Revit/Dynamo/Player/Python и локального JS runtime; не предполагать движок/зависимости. SDK/сборка C# относятся к сохранённому отложенному срезу, см. `tasks/KEO_REVIT.md`.
- Интернет для тестов и сборки не нужен.

**Явное исключение автора 24.10.2026:** разрешено вырезать один предусмотренный проектом круглый проём под проверяемым фонарём только в уже существующей тестовой копии. Точный host, центр, размер и подтверждение хранятся в приватной конфигурации; сначала preview и проверенный rollback, затем отдельный apply. Это исправление тестовой модели не является автоматическим ремонтом BIM, условием работы расчёта на других моделях или разрешением менять исходный RVT. Допущение о предусмотренном проёме сохраняется отдельно от физического исправления. По последующему отдельному разрешению автора результат один раз сохранён в той же RVT, установлен новый контрольный хеш; разрешение на будущие сохранения из этого не следует.

## Команды

Тесты (после **любой** правки расчётного ядра, модели или отчёта — все должны проходить):

```
node test.js              # ядро: 72/72
node test-model.js        # модель/форма/отчёт: источники K, режимы τо/K, ρср, графики Данилюка: 87/87
node bim/test-bim.js      # «КЕО по модели»: 65/65
```

Сверки (вывод не должен меняться без объяснения):

```
node bim/verify-side.js                          # численное интегрирование, примеры АР2
node bim/verify-side.js bim/verify/1226-L01.json # помещения модели 1226
node bim/verify-top.js                           # границы прямой составляющей верхнего света
node verify-danilyuk.js                          # графики Данилюка против АР2 (вывод в verify/)
```

Сборка (после правки исходников — пересобрать и закоммитить сборки **вместе** с исходниками):

```
python3 build.py   # dist/keo.html, dist/keo-standalone.html, docs/index.html
sh bim/build.sh    # bim/keo-bim.js, docs/keo-bim.js
```

`data.js` генерируется `python3 data/build_data.py` из оцифровки СП — руками не править.

## Правила изменений

- **Расхождение с эталоном** (keo.expert, АР2, АР3, точное интегрирование) — сначала объяснить причину; **не подгонять** коэффициенты и округления под эталон. Объяснение — в разд. 7 инструкции проекта.
- Не менять нормы КЕО, MF, климатические коэффициенты, таблицы K, методику r0/r2 и принятую точность округления под видом интерфейсной доработки. Не подгонять n1/n2.
- Каждая формула в отчёте — с номером и пунктом СП; длинные пояснения — сворачиваемые (`<details>`).
- Не объявлять произвольные коэффициенты измеренными; источник каждого значения показывается пользователю.
- Граф Dynamo и Python-исходники хранить в Git вместе с версиями/зависимостями и инструкцией запуска; единственная копия кода внутри несохранённого графа недопустима. MCP/Computer Use — инструменты разработки и проверки, не обязательный runtime пользователя.
- Законченное изменение — отдельный коммит с понятным названием на русском.
- Новые решения и эксперименты сразу записывать в `INSTRUCTION.md` (раздел, журнал разд. 9, версия в шапке).

## Публикация

- Сайт — GitHub Pages из папки `docs/` ветки **`main`**: всё, что попадает в `main`, сразу видят пользователи.
- Работать в отдельной ветке и открывать pull request; в `main` — только после согласия автора.
- Не публиковать, не делать deploy и не менять рабочие расчёты пользователя без явного запроса.
