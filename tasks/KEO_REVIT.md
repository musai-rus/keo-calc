## 1. Цель и границы продукта

Создать локальный инструмент в Autodesk Revit для получения **проверяемого** КЕО каждого выбранного настоящего `Room`: читать исходные данные из BIM-модели, использовать **тот же** вычислительный калькулятор, отображать соответствие на планах и в карточках, записывать сводные результаты в параметры Room, экспортировать входной JSON для существующего веб-калькулятора.

Нельзя объявлять расчёт универсально нормативным только потому, что Room, окно или площадь присутствуют в модели. Универсальность означает отсутствие привязки к именам семейств, конкретному проекту или этажу **и ясное сообщение об ограничениях**, когда данных или поддерживаемой формулы недостаточно.

В рабочем объёме: жилые и общественные здания и схемы расчёта, **фактически поддерживаемые текущим ядром** (`side`, `top`, комбинированный), с неизменёнными нормативными таблицами/округлением; остальные случаи — диагностический статус. СанПиН 1.2.3685-21 ещё не оцифрован; СП 419 для производственных зданий и часть произвольных фасадных схем — бэклог по `INSTRUCTION.md`. Не обещать их полный автоматический расчёт до отдельного этапа и проверки редакций нормативов.

### Уточнение автора 24.10.2026

Проектный расчёт не требует выбранной марки стеклопакета, паспорта изделия или оптических свойств Revit-материала. Использовать нормативные таблицы/формулы для явно выбранной расчётной категории и допустимые нормативные значения при неизвестных характеристиках; остальные принятые проектные допущения подписывать с основанием. АР3 — проверяемый ориентир, а не безусловный источник истины. Различать предписанное нормой значение, выбор строки/диапазона и проектное допущение. Отсутствие данных производителя само по себе не блокирует расчёт, но произвольное число не становится нормативным.

Объём извлечения определяется полями выбранного режима **существующего калькулятора**, а не устройством тестовой модели. Использовать проверенный параметр Revit, минимально необходимое геометрическое измерение либо явный ввод с основанием. Полная обработка тел, граней, материалов и прозрачных поверхностей не является самостоятельным обязательным этапом.

Приоритет: Room → нужные входы → то же ядро → расчёт/норма/причина → цвет помещения и марка на плане; каждый Room можно проверить экспортом в ручной калькулятор. Не исключать действительно нужные размеры, координаты, нормативные входы или затенение ради уменьшения объёма данных.

Другая модель должна требовать выбора помещений/настроек сопоставления параметров, без изменения алгоритма под номер Room, семейство, этаж, ID или путь проекта. Тестовые идентификаторы разрешены только в приватной конфигурации испытаний. Переносимость ещё требуется доказать на другой модели.

Текущая Revit-модель является источником состава и геометрии помещений. Невыпущенный обновлённый АР2 не является зависимостью расчёта. АР2/АР3 проекта используются для проверки подхода подрядчика, схемы и происхождения коэффициентов; старые размеры, номера, результаты и переход на СО автоматически не переносятся. Во время тестов по каждому выбранному назначению проверять нормы в сети и по экземплярам на Google Диске, фиксируя документ, редакцию, пункт/строку и дату проверки. Это проверка при разработке; пользовательский runtime остаётся локальным.

**Явное исключение автора 24.10.2026:** разрешено вырезать один предусмотренный проектом круглый проём под проверяемым фонарём только в уже существующей тестовой копии. Точный host, центр, размер и подтверждение хранятся в приватной конфигурации; сначала preview и проверенный rollback, затем отдельный apply. Это исправление тестовой модели не является автоматическим ремонтом BIM, условием работы расчёта на других моделях или разрешением менять исходный RVT. Допущение о предусмотренном проёме сохраняется отдельно от физического исправления. По последующему отдельному разрешению автора результат один раз сохранён в той же RVT, установлен новый контрольный хеш; разрешение на будущие сохранения из этого не следует.

### Не входит в первый этап

- Переписывание или «улучшение под модель» `engine.js`, `data.js`, `model.js`, подгонка коэффициентов к чужим отчётам.
- Изменение существующих интерфейсов Autodesk Viewer и рабочего калькулятора, сайта, автоматический деплой.
- Изменение исходного RVT, семейства или геометрии ради успешного результата, автоматическое принятие неподтверждённых допущений.
- Автоматическое объявление соответствия всех Rooms всех моделей независимо от качества BIM и применимости нормативов.
- Доведение собственного C#-аддина, его подписи, установщика и WPF/WebView2 до выпуска как обязательное условие Dynamo-прототипа. Это отложенный вариант интеграции после проверки расчётного пути.

## 2. Архитектура и развязка компонентов

**Основной путь:** `Dynamo / Player → Revit adapter → активные входы state v:1 + evidence → неизменённое JS-ядро → карточка/экспорт → отдельная запись цвета и марки`.

1. **Adapter:** выбирает Rooms и контекст, читает поля по [карте входов](../revit-keo/INPUTS.md). Сначала проверенные параметры; геометрия — по необходимости конкретного поля/проверки применимости. Для каждого числа сохраняются источник и единицы. Значения примера из `defaultState()` не являются фактами BIM. Нативные API-объекты не передавать в фоновый процесс.
2. **Подтверждение входов:** проверяются используемая геометрия/координаты, связи/фазы, источники коэффициентов и применимость схемы. Явный ввод допустим и виден пользователю. Неизвестность блокирует только зависящие от неё входы и Rooms. Полный исследовательский D2 остаётся дополнительной диагностикой.
3. **Core bridge / runner:** Python вызывает локальный `runner/runner.cjs` через JSON stdin/stdout. Проверяются наличие основных активных полей, хеши пяти исходных JS-модулей, оригинальные `KEO.migrate()`/`KEO.compute()` и повторный импорт. Runner возвращает результат, предварительный JSON и fingerprint, но сам не подтверждает BIM и оставляет Room серым. D4 связывает вычисление с подтверждёнными входами/нормой. [Контракт D3](../revit-keo/runner/README.md).
4. **Интерфейс:** запуск Dynamo/Player, список Rooms с причинами, карточка и экспорт каждого Room. Целевой результат — подсветка помещений, расчётное/нормируемое КЕО и марки на отдельном плане. Полная WPF/WebView2-панель не является предварительным условием. Player ещё проверяется.
5. **Write-back:** отдельное действие на согласованной копии после предпросмотра и разрешения автора: shared-параметры, отдельный план, цветовая схема, марка/спецификация. Откат через Transaction; сначала read-only цепочка.

**Единственный численный источник истины — основное ядро.** Python измеряет геометрию, но не дублирует формулы КЕО. Версию/хеш ядра, state и происхождение входов сохранять. Неактивные секции state служат совместимости импорта и не требуют извлечения дополнительной геометрии.

**Инструменты:** MCP/Computer Use используются при разработке, не обязательны для запуска пользователем. JS runtime выбирается явно, без скрытой зависимости от среды агента, текущей папки, сети или AI. Viewer — отдельный эксперимент. C#-исходники сохранены в `revit-keo/native/`; подпись/установщик отложены, заблокированную DLL через Dynamo не загружать, защиту Windows не менять.

**Безопасность модели:** повторно использовать прежнюю standalone тестовую RVT. Исходник не изменять, новых копий на каждый запуск не создавать. Сверять активный документ/экземпляр; D0–D4 не сохраняют RVT и не записывают параметры/виды. Контролировать `IsModified`, версию документа и хеш до/после. Посторонние несохранённые правки автоматически не отменять. Прежнее разовое разрешение на сохранение копии не разрешает будущие сохранения.

## 3. Отбор Rooms и необходимые входы

- Выбор по параметру Room и точному значению, по уровню/списку или одному Room на плане. Показывать ID/GUID, тип/доступные значения параметра, число совпадений и пустые значения. Номера/этажи пользовательской модели не вшивать в алгоритм.
- Идентичность — документ, `Room.UniqueId`, фаза/вариант, путь экземпляров связи и transform. Имя/номер — подпись, не ключ. Не объединять Rooms в одно нормативное пространство автоматически.
- Сначала выбрать профиль и состав нужных полей по [INPUTS.md](../revit-keo/INPUTS.md). Проверить размещение/замкнутость Room и пригодность формы для выбранной схемы. Полный набор контуров/тел/материалов не является обязательным экспортом.
- Параметр допустим после проверки смысла, единицы и экземпляра/типа. Иначе использовать необходимое измерение или явный ввод с основанием. Настройки сопоставления меняются для другой модели без изменения кода.
- Проёмы: нужны используемые размеры/положение, связь с Room и поддерживаемая схема. Габарит семейства не считать доказанным расчётным проёмом; не определять тип по имени семейства. Размер должен соответствовать принятому в калькуляторе обмеру и коэффициентам. Не заменять автоматически проём чистой площадью стекла и не учитывать рамы дважды.
- Для бокового света нужны используемые размеры фасада/проёмов/точки; для верхнего — поля выбранного типа фонаря/шахты/надстройки и разреза. Высота помещения нужна там, где её использует выбранная схема. Неизвестную форму не заменять прямоугольником/кругом по догадке.
- Затенение учитывать в схемах текущего калькулятора: параметры его таблиц/коэффициентов и противостоящих зданий с проверенной применимостью. Лучи/подробная 3D-геометрия нужны, когда без них нельзя получить или проверить нужный вход; это не обязательный этап для любого Room. Ноль найденных препятствий не доказывает их отсутствие.
- Фильтр Rooms не исключает релевантное окружение вне выбранных помещений. Связи/север/фазы/единицы проверять в части, влияющей на нужные поля. Недоступная нерелевантная таблица, материал или кривая не блокируют расчёт всех Rooms.
- Ошибка API, неизвестная единица/привязка или нехватка обязательного входа дают конкретную диагностику этого Room. Остальные продолжают обработку. Неизвестность не превращать в ноль или подтверждённое отсутствие затенения.

**Параметры условных семейств:** расчётный смысл параметра, единицу и область экземпляр/тип проверять до использования. Сопоставление задаётся настройкой проекта (GUID/ID либо однозначное имя), без встроенных названий семейств и проектных значений. Верхний и нижний проёмы независимы; радиус явно переводится в диаметр, если поле калькулятора требует диаметр. При подтверждённом автором условном представлении фонаря декоративные расширения, скругления и наружный габарит стекла не заменяют проектный размер светового отверстия. Расхождение сохранять в evidence вместе с решением автора; это не универсальное разрешение игнорировать реальные препятствия. При отсутствии/неоднозначности параметра — необходимый обмер или явный ввод с основанием; автоматическая догадка запрещена. Переносимость проверяется на другой модели, а не одинаковыми именами параметров.

## 4. Расчёт, нормы и статусы

- Перед геометрическим сбором определить нормативное назначение: подтверждённая норма → нужные поля выбранной схемы; подтверждённое отсутствие нормы → EXCLUDED/серый «КЕО не нормируется» со ссылкой на строку; неизвестное назначение → PENDING. Отсутствие строки в оцифрованном справочнике само по себе не означает отсутствие нормы. Не назначать переговорной норму рабочего кабинета только по принадлежности к административному блоку. Функция рабочего места, включая специальное оборудование, может требовать иной строки; неоднозначность сохранять явно.

- Режим освещения: боковой, верхний (зенит/шахта или надстройка), комбинированный. Выбор режима — на основе подтверждённых входов и применимости схемы + явных решений пользователя. Не подтверждённый режим — без окончательного вердикта.
- Регион/группа светового климата, назначение здания/помещения, нормы ЕО/СО, расчетная точка, направление фасада и коэффициенты должны иметь источник из модели, справочника или явного ввода. Не угадывать климатическую группу по адресу; если назначения/нормы недостаточно — серый.
- Применяются только поддерживаемые СП, формулы и точность существующего ядра. Вердикт следует `KEO.compute` с проверкой всех используемых входов и нормативного назначения. Расчётное число без подтверждённых используемых входов/нормы **не** равно доказанному соответствию.

| Цвет | Код | Условие |
|---|---|---|
| Зелёный | `PASS` | Полностью подтверждены входные данные, актуальность, методика и нормируемое значение; ядро вернуло соответствие. |
| Красный | `FAIL` | Те же доказательства подтверждены; ядро вернуло несоответствие. |
| Серый | `PENDING` / `EXCLUDED` / `STALE` / `ERROR` | Недостаточно данных, помещение исключено, нужна ручная проверка, изменена модель/норма, расчёт не поддерживается или завершился ошибкой. Подтип и причина обязательны. |

До подтверждения исходных данных разрешены **диагностические или предварительные числа с маркировкой**, но не зелёный/красный. При изменении RVT, параметров входа, геометрии связанных моделей, набора норм или версии ядра сравнивать fingerprint и переводить устаревший итог в `STALE`, не показывать прежнюю зелёную заливку как действующую.

## 5. Интерфейс и BIM-результат

1. **Интерфейс запуска (сначала Dynamo/Player + локальный отчёт):** выбор параметра и значения, уровня/Room, региона, назначения/системы света, действие «Проверить пригодность», «Рассчитать», журнал ошибок; фильтр по этажу и состоянию. По умолчанию возможен первый проход по всем подходящим Room, после чего пользователь уточняет назначения и запускает повторный расчёт без потери верифицированной геометрии.
2. **Карточка Room:** номер, имя, уникальный ключ, уровень/фаза, площадь (Revit и расчётная сверка), тип света, координаты и обоснование расчётных точек, окна/витражи/фонари и затенение с устойчивыми ID, происхождение каждого используемого входа, нормативное/расчётное КЕО, формулы/коэффициенты и источники, точность/проблемы, дата и версия расчёта; выбор элемента подсвечивает его в Revit. Подробный расчёт — раскрываемая панель и/или HTML/PDF, не гигантский текстовый параметр.
3. **Общие параметры Room** (рабочие имена, закрепить GUID и спецификацию типов перед внедрением): `KEO_Рассчитывать` (Yes/No), `KEO_Статус` (Text), `KEO_Расчётный` (Number), `KEO_Нормируемый` (Number), `KEO_Тип_освещения` (Text), `KEO_Примечание` (короткая причина/ссылка), `KEO_Дата_расчёта` (Text/Date по возможностям API), `KEO_ID_расчёта` (Text). Единицы чисел — **процент КЕО**, точно обозначить в описании и форматировании. Сначала проверить существующие одноимённые параметры и конфликт GUID, не перезаписывать чужие значения.
4. **Отдельные планы «КЕО — расчёт»**, фильтры/цветовые схемы, Room tags с номером и КЕО %, при желании нормой/статусом; спецификация по выбранным уровням. Выделение зелёным/красным/серым без изменения исходных архитектурных видов. В Revit визуально проверять соответствие цвета данных карточке и спецификации. Готовые семейства марок создавать/подключать только после согласования внешнего вида и теста на копии.
**Согласованный вид марки (24.10.2026):** три строки — номер помещения; «КЕО …% / норма …%»; статус. До приёмки — «предв.» и «Уточнить». Согласование внешнего вида выполнено; создание/подключение и проверка связанной численной RoomTag ещё не выполнены.

5. **Запись в модель** отделена от read-only расчёта: отдельная кнопка и подтверждение состава изменений; отдельная транзакция, rollback при ошибке, лог затронутых элементов. Никакая диагностика не должна случайно помечать документ изменённым.

## 6. Контракты JSON и доказательств

**На каждый Room** должны быть доступны два независимых экспорта:

1. **`<room-key>.keo.json` — вход ручного калькулятора.** Совместимый с текущим импортом объект `v: 1` и поля `side`, `top` (а также корректные `mode`, `region`, `group`, `roomId`, `lightSys`, `meta` и остальные поля по `KEO.defaultState()`/`KEO.migrate()`). Он содержит **только** подтверждённый расчётный state, проходит валидацию текущего калькулятора и даёт при импорте **те же численные результаты**. Не изобретать «новый Revit JSON» вместо него и не вмешивать служебную диагностику в расчётные числа. Для неполного/сомнительного входа не предлагать валидный расчётный state под видом принятого; доступен диагностический пакет.
2. **`<room-key>.evidence.json` — диагностика.** Версия схемы, устойчивый ID модели/Room/связей, версии Revit/API/Dynamo/Python-движка/JS runtime, commit и хеши графа/скриптов/ядра, дата, fingerprint, фаза, используемые значения/единицы и необходимые координаты, цепочка происхождения и преобразований, рассчитанные параметры и причины отказов, результаты сверки, признак `previewOnly`/допуск к окончательному вердикту. Для долговременного архива сохранять исходные факты и решения пользователя. Полная копия геометрии/материалов сцены не требуется; нужны воспроизводимые источники активных входов и решения. Доказательный JSON нельзя автоматически выдавать за импортируемый «state калькулятора».

Импорт совместимого JSON в локальную неизменённую сборку калькулятора и сравнение полей/state/result — обязательный acceptance test. Учитывать повторные номера Room: имя файла и ID расчёта не должны основываться исключительно на номере. Нельзя включать в GitHub реальные RVT, персональные пути/секреты и приватные исходные данные заказчика.

Для верхнего/комбинированного света приёмка включает все применимые критерии: среднее, минимум в каждой точке и равномерность по СП 52 п.5.13, а не только численный pass ядра. Проверка этих критериев не разрешает изменение формул ядра. [Протокол нормативного отбора](../revit-keo/dynamo/NORMS.md).

## 7. Проверка и критерии приёмки

Готовность подтверждается воспроизводимым результатом, не одним скриншотом/сборкой.

| Этап | Проверяемый результат | Предел |
|---|---|---|
| A. Среда | Версии, read-only запуск, отмена/повтор, контроль RVT | Не доказывает другие установки |
| B. Room | Устойчивый выбор/идентичность, контекст и необходимые параметры/геометрия | Не является нормативным КЕО |
| C. Активные входы | Каждое используемое поле имеет проверенное значение, источник/единицу/применимость; независимая сверка нужных размеров | Не требует проверки всей сцены и не подтверждает неподдерживаемые схемы |
| D. Core/JSON | Совпадают state/result/вердикт неизменённого калькулятора после импорта; ошибки/отмена/тайм-аут контролируются | Синтетика не подтверждает реальные входы Room |
| E. BIM-результат | Карточка/экспорт, три цвета/причины, отдельный план, марка/спецификация, безопасная запись/rollback | Нужна визуальная проверка в Revit |
| F. Переносимость | Несколько Rooms разных типов/уровней, минимум другая модель без изменения кода, повтор/stale | Не обещает расчёт любой формы |

Для первого профиля обязательны отрицательные проверки: неразмещённый/неограждённый Room, неподходящая схема, недостающий активный вход, одинаковые номера, ошибка единиц/фазы/привязки, неподтверждённая норма/затенение, ошибочный коэффициент, изменение входов, сбой runner. Ошибка одного Room не останавливает пакет и не даёт ложный зелёный/красный.

При записи проверить конфликт GUID/параметров, совпадение марки/цвета с карточкой, отмену/rollback. При расширении D6 проверять витражи, несколько фасадов, фонари/пересечения, наклонные/связанные модели и сложное затенение. До реализации такие случаи диагностируются; они не блокируют завершение простого профиля. Конкретные этажи/семейства текущего проекта не являются критерием универсальности.

Тесты ядра/модели/Viewer не менять по смыслу. После правок ядра/модели/отчёта обязательны команды AGENTS.md; для адаптера — подходящие проверки его слоя. Синтетические, реальные Dynamo и GUI-тесты фиксировать раздельно.
