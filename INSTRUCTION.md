## 1. Цель

Веб-калькулятор для проверочного расчёта КЕО помещений жилых и общественных зданий, доступный по ссылке. Пользователь (архитектор) вводит то, что снимает в Revit, получает:

- расчётный и нормируемый КЕО, вердикт **СООТВЕТСТВУЕТ / НЕ СООТВЕТСТВУЕТ**;
- полный разбор: каждая формула, подстановка чисел, источник каждого коэффициента (пункт/таблица СП);
- PDF-отчёт на листах А4 с рамкой и основной надписью (как в 1226-30-01-АР2/АР3).

Принципы UI: простой, не перегруженный; пошаговый ввод; рядом с человеческим названием параметра — его обозначение из формулы (например, «Высота подоконника, hпд, м»); весь объёмный текст (выдержки из СП, разбор формул) свёрнут по умолчанию.

## 4. Методика и принятые решения

### 4.1 Боковой свет, (Б.1)
eрб = CN · [Σ εбi·q(γi) + Σ εздj·bфj·Kздj] · r0 · τ0 · K · MF

- **n1, n2 считаются аналитически**, без ручного наложения графиков Данилюка. Графики I и II — это графическая запись точных формул для равнояркого неба:
  - n1 = 50·(cos θн − cos θв), θ — углы возвышения нижней и верхней границ видимого через проём участка неба в разрезе (с учётом толщины стены: низ — по ближнему к точке ребру подоконника, верх — по наружному ребру перемычки);
  - n2 = (100/π)·Σ(ψ + ½·sin 2ψ) по обе стороны оси, где tg ψ = y·cos γ / x — боковой угол в наклонной плоскости через точку и середину C1 видимого участка (выбирается наиболее ограничивающее ребро откоса — внутреннее или наружное);
  - γ — угол возвышения середины видимого участка проёма (одинаков для внутренней и наружной плоскости стены).
  - Проверено: совпадает с keo.expert (АР2, прил. 1: n1 = 6,1; n2 = 20,5; γ = 19,02°).
- q(γ) — по формуле (3.2): q = 0,429·[1 + 4·exp(−0,7 / sin γ)] (а не старая таблица МКО).
- Каждое окно — отдельный «участок неба» (сектор). Окна разной ориентации — расчёт отдельно и сумма (п. 8.4.1, прим.).
- r0 — табл. Б.6 (УРП) / Б.7 (пол), трилинейная интерполяция по dп/h01, lт/dп, bп/dп и ρср.
  - **h01 — высота верха окна над УРП 0,8 м и для точки на полу** (заголовок табл. Б.7 и практика keo.expert; проверено: 1,27 % в АР2 прил. 1).
  - За пределами табличных диапазонов значения **не экстраполируются, а принимаются по ближайшей границе** (так делает keo.expert; консервативно). Это фиксируется в отчёте.
  - Табличные параметры dп/h01, lт/dп, bп/dп **округляются до сотых** перед интерполяцией (так делает keo.expert; проверено — r0 совпадает до 4 знаков в 4 примерах).
- Число лучей n1, n2 **округляется до десятых** (точность графика), εб = 0,01·n1·n2 по округлённым значениям — числа в отчёте пересчитываются экспертом вручную.
- Окна разбиваются на участки по границам противостоящих зданий (как секторы в keo.expert): для каждого участка свои n1, n2, γ.
- Kзд0 — табл. Б.8 при (lт+Δст)/dп (по тексту таблицы «от наружной стены»); с keo.expert расхождение до 0,03 по Kзд0, влияние на e < 0,1 %.
- K (табл. Б.17–Б.20) — интерполяция и экстраполяция по примечаниям (совпало с keo.expert: 0,43 для козырька 3,25 м).
- Противостоящие здания — схема № 1 (параллельно). Для каждого здания: расстояние l, расчётная высота Hр (от пола помещения), длина a, ρф. Считаются n1′, n2′ (те же формулы), εзд = 0,01·n1′·n2′, bф — табл. Б.1 по l/a и a/Hр, z1, z2 — по рис. Б.4, Kзд0 — табл. Б.8, Kзд — по (Б.7).
- K — табл. Б.17–Б.20, интерполяция по глубине помещения и глубине элемента.
- τ0 = τ1·τ2·τ3·τ4·τ5 (Б.8): τ1 — табл. Б.13/Б.14 (выбор стеклопакета словами), τ2 — Б.15, τ4 — Б.16, τ3 = τ5 = 1 при боковом.
- MF — табл. 5.1 СП 367 (по условиям среды и наклону остекления), с поправками 0,91 / 1,11.
- CN — табл. 5.1 СП 52 по группе района (прил. Е) и ориентации.
- Положение РТ — по п. 5.3 СП 52 (автоподсказка по назначению: центр / 1 м от дальней стены / 1,2 м; пол / 0,8 м) с возможностью переопределить.
- **Источник K (13.10.2026)** — в форме, разборе и PDF: «СП 367.1325800.2025, табл. Б.17 (балкон) / Б.18 (лоджия) / Б.19 (козырёк) / Б.20 (экран)», вынос, глубина помещения, положение точки, способ (узел / интерполяция / экстраполяция, ограничение 0…1). Нет элемента — «K = 1,00; затеняющие элементы отсутствуют». Ручной K — «задано вручную … : основание» (для стены — пункт «Задать K вручную», для проёма — исключение). Значения таблиц K не менялись (тест сравнивает 200 сочетаний).
- **Коэффициенты проёма (13.10.2026).** Общие τо и K стены — вычисляемые, только для чтения («по общим параметрам стены»). У каждого проёма для τ2, τо и K — режим «По общим» / «Вручную» и «Очистить». Приоритет: ручное значение проёма заменяет общее (не умножается); ручной τо заменяет всё произведение τ1…τ5 (τ2 проёма помечается «не используется», значение сохраняется); при авто-τо τ2 проёма заменяет общий τ2. Единая функция `KEO.winCoef` даёт значение и источник для ядра, формы и отчёта (таблица «Происхождение τо и K по проёмам»).
- **Ввод ручных коэффициентов**: пусто/null — не задано; «0,36» = «0.36»; нечисловая строка, ±∞ — ошибка; τ1 по паспорту, τ2, τо, K — диапазон (0; 1], **ноль недопустим** (проём без пропускания удаляется из расчёта); ρ поверхности — [0; 1), ноль допустим; ρср вручную — (0; 1). Ошибка ввода — «Не хватает данных», результат не выдаётся. Файлы прежних версий без режимов: «вручную», если значение задано и не ноль (как прежняя проверка истинности); ноль — «по общим» с замечанием при открытии.
- **Проверка по графикам Данилюка I и II** (разбор → «Геометрический КЕО», PDF): выбор стены, проёма и участка; совмещённые разрез (график I, полюс в А, полуокружность через C) и план (график II, полюс P на оси через А на расстоянии R от наружной грани) в одном масштабе; таблица отсчётов (n1/n2 по графику, аналитика до округления, в расчёте) и вкладов (ε, γ, q, вклад в e, τо, K). Видимая область строится заново по рёбрам проёма (независимо от ядра); отсчёт границы — по ближайшей пунктирной линии десятых. Затеняющие элементы лучи не обрезают (п. 8.4.2), противостоящие здания — отдельные участки. Метод расчёта не менялся.

### 4.2 Верхний свет — зенитные и шахтные фонари, (Б.3)
eрв = CN·τ0·MF·[100·Aф.в·Σ q(αi)·cos^(2+2/Kс)(αi) / (π·hр²) + εср·(r2 − 1)]

- α = arctg(lф / hр) из горизонтального расстояния до центра фонаря в плане (пользователь не вводит углы); q(α) = q(γ = 90° − α) по (3.2).
- iф: прямоугольная шахта — (8.2) 4(Aв+Aн)/(√π·hс.ф·(Pв+Pн)); круглая — (8.3) (rв+rн)/(2hс.ф).
- Kс — оцифровка рис. Б.2 (диффузное отражение стенок) / Б.3 (направленное), кривые ρ = 0,5…0,9, интерполяция.
- r2 — табл. Б.21 по hр/l1, числу пролётов и ρср.
- τ0 — τ1 (остекление верхнего отверстия), τ2 (переплёт), τ3 (несущие конструкции), τ4, τ5 = 0,9 при защитной сетке.
- MF — по углу наклона остекления (обычно 0°–15° → 0,67 для норм. условий).
- Точки: равномерно по линии характерного разреза, первая/последняя — 1 м от стен. При L > 4 м автоматически 5, вручную допускается увеличение; менее 5 блокируется (п. 8.5.2). При 2 < L ≤ 4 м автоматического правила «3 точки» нет: пользователь явно выбирает число точек и указывает основание проектного решения, которое выводится в отчёте. Интерфейс поддерживает 3, 5, 7, 9, 11 точек; сохранённые значения 3…101 также читаются (это диапазон программы, не требование СП). При L ≤ 2 м расчёт блокируется: крайние точки с отступом 1 м не образуют допустимый разрез, нужна отдельная схема. Правило общее для верхнего и комбинированного света, Б.2 и Б.3.
- Координаты центров зенитных/шахтных фонарей можно вводить от нижнего левого угла или от центра прямоугольного помещения: x вправо вдоль L, y вверх вдоль B; отрицательные координаты от центра допустимы. Внутри модели и JSON координаты всегда хранятся от угла; `top.coordOrigin` задаёт только способ ввода/отображения. Переключение не меняет физическое положение, расстояния lф и КЕО; старый JSON без этого поля читается как «от угла». При изменении L/B сохраняется положение от стен, а показанные координаты от центра обновляются. Линия разреза y0 по-прежнему отсчитывается от стены y = 0. План и PDF показывают начало/направления осей; отчёт содержит таблицу координат в выбранной системе. Старые короткие расчёты требуют явного выбора точек и обоснования вместо скрытого авто-3.
- eср — (Б.10) (трапеции), равномерность — emin/eср ≥ 1/3 (п. 5.13 СП 52).
- Несколько типов фонарей — расчёт по типам и суммирование в точках (как в АР3).
- Пересечение верхних или нижних отверстий фонарей на плане блокирует расчёт и выгрузку PDF: модель суммирования отдельных фонарей не должна повторно учитывать перекрывающиеся отверстия. Проверяются все пары внутри типа и между типами: круг–круг, прямоугольник–прямоугольник, круг–прямоугольник по фактическим контурам, отдельно для верхнего и нижнего отверстия. Сообщение содержит номера типов/фонарей и уровень пересечения. Касание без перекрытия площади не блокируется (численный допуск 10⁻⁹ м); эта проверка не назначает конструктивные зазоры и не заменяет проверку объёмов наклонных стенок шахт. Действует в верхнем и комбинированном режимах, при ручном вводе и загрузке JSON, независимо от начала координат.
- π — точное значение (в Excel было 3,14 → расхождение ~0,05 %, допустимо).

### 4.3 Округление
Промежуточные значения храним с полной точностью; в отчёте показываем 2–4 знака; итоговый КЕО округляем до сотых (п. Б.2.12 СП 367, п. 5.9 СП 52). Вердикт — по округлённому значению: eр ≥ eн.

### 4.4 Верхний свет — фонари-надстройки и проёмы в покрытии, (Б.2)
eрв = CN·[Σ εвi·q(γi) + εср·(r2·kф − 1)]·τо·MF

- Виды: прямоугольный (П), трапециевидный, А-образный, шед с вертикальным и с наклонным остеклением, проём в плоскости покрытия (ленточный / штучный). Профиль задаётся в поперечном разрезе: ширина проёма в покрытии b, борт hст (от плоскости проёма до низа остекления), высота остекления hо, наклон β; положение — оси фонарей x; вдоль оси — начало, длина, число штук и шаг.
- n1: в поперечном разрезе строится полная видимость из точки — стены, покрытие с проёмами, борта, покрытие фонаря, скаты шедов, **соседние фонари** (луч, который после остекления упирается в другой фонарь, не учитывается). Для каждого остекления — интервал углов φн…φв, n1 = 50·|cos φн − cos φв|.
- C — середина видимой части остекления, R = |AC|, γ — угол возвышения C. n2 — график II на горизонтали № R; торцы проёма на уровне покрытия (ниже C на zC − Hк) тоже ограничивают луч (как на продольном разрезе).
- **εср = среднее по точкам значений Σ εв·q(γ)** — по шагам п. 8.5.1 г), е) СП 367 (εв в первой точке = 0,01·Σ(n1·q·n2)); так же устроен метод для шахт (8.4)–(8.7) и пример в СП 23-102-2003. Если экспертиза трактует εср без q — отражённая составляющая изменится на величину q (≈ 1,0–1,25).
- kф — табл. Б.22 (ленточные 1,0; штучные 1,1; трапециевидные 1,15; прямоугольные 1,2; шед наклонный 1,3; шед вертикальный 1,4). А-образный — как «наклонное двустороннее остекление» (1,15) — допущение, в таблице отдельно не назван.
- CN — табл. 5.1 СП 52: строка выбирается явно (прямоуг./трапец. С-Ю, СВ-ЮЗ/ЮВ-СЗ, В-З; шед С; горизонтальные — как зенитные). MF — по наклону остекления (табл. 5.1 СП 367). r2 — табл. Б.21 по hф/l1 (hф — от УРП до низа остекления), l1 по умолчанию = L / число пролётов.
- Несколько типов фонарей — по каждому типу свои kф, τо, CN, MF и εср; КЕО в точке суммируется; заслонение считается совместно.
- Проверка: число лучей сверено с точным интегрированием по небосводу (равнояркое небо) для всех видов — расхождение < 1 %. Контрольного примера с числами в исходных материалах нет — первое реальное помещение стоит сверить вручную по графикам.
- Ограничение метода (не программы): q берётся по углу γ в плоскости разреза; точное интегрирование по небу МКО даёт для длинных фонарей прямую составляющую примерно на 8 % ниже. Программа следует нормативной методике.

### 4.5 Средневзвешенный коэффициент отражения ρср (13.10.2026)
- Режимы: **«0,55 — коэффициенты неизвестны»** (примечание 2 к табл. Б.6/Б.7); **«По поверхностям»** — формула (3.6), п. 3.13 (общее определение), состав при боковом — примечание 2 к табл. Б.6/Б.7: пол, стены, потолок, **окна** (окна не исключаются); для r2 верхнего света — табл. Б.21: пол, стены, потолок; **«Вручную»** — одно значение и основание. Ручная правка поля ρср переключает режим на «Вручную».
- Площади по размерам (прямоугольное помещение, плоский потолок): пол и потолок a×b, стены 2(a+b)H − Sок, окна Σ bо×hо (наружный обмер коробки, п. Б.2.7 — приближение для внутренней поверхности). Ручная площадь стен — **уже без окон**. Ручные площади не пересчитываются (предупреждение). Сложный контур — ручная ведомость. Оболочка считается один раз: при двух стенах габариты должны совпадать (или поменяться местами) — иначе ошибка. Перекрывающиеся проёмы, проём за стеной, отрицательная площадь, нулевая сумма — ошибка до выдачи результата.
- ρ поверхностей по умолчанию **не подставляются** (пустые поля); 0,20 из п. Б.2.3 относится к окнам противостоящих фасадов. В источнике ρ пользователь указывает: измерения / паспорт / ориентир.
- Применяемое ρср округляется **до сотых** (как аргументы табл. Б.6/Б.7, Б.21), точное значение выводится рядом (контроль: 17,7/60/17,7/6 и 0,25/0,40/0,70/0,20 → 0,4143491124 → 0,41). Кнопки «Принять» нет — расчёт всегда использует текущее состояние.
- Файлы прежних версий (нет режима ρср): **всегда «источник не подтверждён»**, число сохраняется — в том числе 0,55: оно могло быть введено вручную или получено расчётом, по самому числу режим не определяется (решение автора 14.10.2026, вместо прежнего «0,55 без помощника → «0,55»»). Если число совпадает с прежним помощником — это указывается, площади не подменяются. Нет числа в файле — ошибка до выбора режима (0,55 не подставляется). Новый расчёт по-прежнему начинается с режима «0,55».
- Комбинированный режим: одно ρср для r0 и r2 (как и раньше) — указано в отчёте; раздельные ρср — вопрос автору (разд. 11).


## 5. Архитектура

- Один самодостаточный HTML-файл (весь CSS/JS/данные внутри), без сервера и без внешних запросов → работает по ссылке claude.ai и с любого статического хостинга (wiki, GitHub Pages).
- Модули внутри: `DATA` (оцифрованные таблицы с указанием источника), `Engine` (чистые функции расчёта, возвращают результат + журнал шагов для отчёта), `UI`, `Report` (HTML-разметка листов А4 → печать в PDF через браузер, `@page A4`).
- Каждый шаг журнала: обозначение, название, формула, подстановка, результат, источник (пункт/таблица).
- Сохранение/загрузка исходных данных в JSON (для повторного расчёта и архива).


**КЕО для Revit (решение 23.10.2026):** основной ближайший прототип — Dynamo/Dynamo Player → Python + официальный Revit API → проверяемая геометрия/evidence → локальный вызов неизменённого JS-ядра → карточка/отчёт и совместимый JSON. Python может выполнять сложные геометрические алгоритмы, но не дублирует формулы КЕО. Существующий C#-срез сохранён как отложенный вариант; подпись/загрузка DLL не является условием начала Dynamo. Среда прошла D0, минимальный D1 читает один Room в Main Model с нативными Line/Arc и независимой сверкой метрик. Проёмы/затенение, runner и нормативный результат ещё должны пройти приёмку. Требования и этапы D0–D6 — [ТЗ v0.2.2](tasks/KEO_REVIT.md); выполнение — [Issue #13](https://github.com/musai-rus/keo-calc/issues/13), изменения — [PR #15](https://github.com/musai-rus/keo-calc/pull/15). Работать на существующей тестовой копии RVT; запись в модель отдельным этапом. Viewer остаётся самостоятельным экспериментом.

### КЕО по модели в окне Autodesk Viewer (bim/)

- **Временные сечения и восстановление вида (18.10.2026, локально, не опубликовано).** `withFullModel` сохраняет named cut-plane sets через согласованный полный API Viewer, а при его отсутствии поддерживает проверяемый legacy getter/setter. Общее сечение не записывается в один owner. После ошибки предпринимается восстановление каждого доступного исходного набора с обязательной итоговой проверкой; неподтверждённое восстановление отменяет результат. Один per-Viewer scope удерживает сечения снятыми до завершения всех вложенных/перекрывающихся стадий. `3D` доступен после отмены для восстановления вида, но не сбрасывает dirty и не обходит проверку модели/размещения или запрет экспорта. `bim/test-cut-sets.js` моделирует aggregate getter/single-owner setter, отказы API и async-перекрытие; live-проверка ограничена коротким native API probe, новая полная сборка в открытый Viewer пока не установлена.
- **Идентичность PDF (18.10.2026, локальное исследование).** Перед category/property lookup raw VBR ID преобразуется через `model.remapDbIdFor2D`; `reverseMapDbIdFor2D` обязан вернуть исходный raw ID. Отсутствие/невалидность remap не разрешает прямое чтение raw как dbId. `bim/pdf-identity.js` — отдельный read-only helper, не включён в `keo-bim.js`: `map(model, rawId)` возвращает source identity и пару ID, `read(model, rawId)` добавляет свойства и externalId с повторной проверкой после await. Проверяется согласованность концов чтения; переход A→B→A и замена объекта с теми же метаданными не обнаруживаются. Актуальную привязку и поколение Viewer обязан проверять вызывающий код. Он не удостоверяет текущий Viewer, геометрию, точность экспорта или смысл графики; вызывающий код отдельно проверяет актуальную привязку. Filled polygons/hatches, линии, glyphs, марка и leader должны различаться по источнику. Наличие ID, bbox и сходство площадей не доказывают Room perimeter или внутренний seed.

- **Confidence назначения (18.10.2026, локально, не опубликовано).** Статус inference управляет допуском нормативного вывода: supported допускает прежнюю предварительную оценку; tentative/ambiguous/unknown требуют явного выбора известного назначения пользователем. Ручной выбор хранится по модели. Для неподтверждённого варианта C.norm/comb.norm не имеют численного значения, normOk/pass/uniOk равны null; значение КЕО само по себе не подтверждает выбор точки или методики. Экспорт с такой геометрией содержит предварительные исходные с предупреждением, а не готовый state калькулятора. Геометрическая достоверность остаётся отдельным условием.

- **Локализованные категории и накопление сценариев (18.10.2026, локально).** Каноническая категория определяется служебным CategoryId/BuiltInCategory, а не именем элемента или семейства. Допустимый запасной путь — точные ru/en имена категории при отсутствии идентификатора; unknown и противоречия явно сохраняются в диагностике. Rooms/Spaces/Areas не смешиваются. Наличие записи Room в propertyDB не требует fragments и не доказывает native границы. Типизированная строка имени уровня, включая ведущие нули, отличается от внутренней ссылки. Одинаковый resolver используется в bulk-каталоге и worker; единицы численных свойств сохраняются со своим исходным значением. Реестр bim/SCENARIOS.md развивается при новых случаях; исчерпывающего покрытия не заявляется.

- **Привязка к текущему Viewer (18.10.2026, локально, не опубликовано).** Глобальная ссылка NOP_VIEWER считается лишь кандидатом. При отключённом/скрытом canvas, нескольких видимых Viewer или нескольких загруженных моделях, незавершённой загрузке, 2D или несоответствии root document URN маршруту Autodesk `/id/` расчёт остановлен. Для встроенного Viewer без такого маршрута требуется единственный видимый подключённый экземпляр; источник идентичности — сам документ модели. Снимок включает ссылки на Viewer/model/DOM/document, root/derivative URN, view GUID и URL. После асинхронных стадий и до сохранения/показа результат проверяется повторно. Наблюдатель отменяет показ и очищает данные при смене модели, включая нулевой результат и ожидание базы свойств. Выбор первого найденного Viewer и исправление глобальной ссылки не выполняются. Проверки — синтетические unit/lifecycle; сохранённый live-прогон опубликованной версии после обычной перезагрузки отдельно от исправления.

Множество возможных ближайших образцов — диагностика с контрактом точности, не нормативный центр и не разрешение расчёта. См. `bim/EXPLICIT-POINT-UNCERTAINTY.md`.

Ручной короткий разрез при недостаточном доказательстве блокируется. Состояния «подтверждено», «противоречие» и «недостаточно данных» относятся к указанной геометрической проверке, не к нормативной достоверности КЕО всего проекта. - **Два растра.** R — стены, витражи, двери, окна, колонны и линии разделения помещений: по нему опознаются помещения Revit (площадь ±4 % в чистоте или до осей стен + периметр 0,75…1,45). Rp — только физические преграды: по нему определяется расчётное пространство, видимость окон и сечение. Линии разделения светопрозрачны и стенами не считаются.
- **Расчётное пространство** — связная область Rp (физический объём). По умолчанию все неисключённые помещения объёма — одно пространство (групповая + спальня с перегородкой, не доходящей до витража). Исключённые (ЛК, коридоры, холлы, вестибюли — настройка) автоматически не объединяются, показываются как «открытый проход». Если в объёме несколько помещений одного назначения (две спальни) — считаются раздельно с пометкой «уточните состав». Ключ помещения — ElementId (не номер). Мелкие свободные части (< 8 м², полосы у витражей) делятся между пространствами объёма по близости; крупные части без помещения (≥ 8 м²) не присоединяются.
- **Помещения без контура** (нет линии разделения): к свободной части объёма подбираются 1–3 неопознанных помещения с той же суммой площадей (±3 %, периметр совместим). Назначается автоматически, только если вариант единственный; иначе показываются варианты, выбор — кнопкой «Это они». На модели 1226 варианты неоднозначны (групповые 30/39/102 по 64,75 м², раздевальные по 21,57 м²) — требуется решение пользователя.
- **Ручные решения** (объединить / считать раздельно / помещения в контур / назначение по табл. А.1) хранятся в браузере по URN модели, экспорт и загрузка — JSON. Повторный расчёт уровня — без нового среза.
- **Площадь**: свойство Area с dataTypeContext → м² явным переводом (м², мм², см², фут², дюйм²); неизвестные единицы — значение не используется, предупреждение. В карточке — площадь Revit (сумма без повторов), площадь контура в чистоте и до осей, расхождение; > 5 % — предупреждение. Для расчёта используется контур (L, B, dп), площадь Revit — для сверки.
- **Боковой свет (Б.1)**: окна — прозрачные фрагменты окон, витражных панелей и дверей; панели одной плоскости — в окна, окна — в стены. Для точки учитываются только видимые участки остекления (луч от точки до внутренней грани проёма по Rp; перегородка — препятствие). Точка — в помещении, определяющем норму (наибольшая норма из помещений пространства), по правилу п. 5.3 СП 52 для основной стены; центр — если значимое остекление (≥ 25 % основной) в нескольких стенах. bп и ось — по свободному сечению через точку параллельно стене (колонны пропускаются, перегородка — граница).
- **Фонари** (с 08.10.2026, задачи Slack 18:16): кандидаты — стекло, обращённое вверх (доля площади стекла с наклоном ≤ 60° > 0,5), или элемент с «фонарь/зенит/skylight/roof light/мансардн/световод/купол» в имени; категории — окна (в т. ч. семейства «Окна» в кровле), витражные панели, кровли, обобщённые модели, Skylights; двери фонарями не считаются, перекрытия и потолки — тоже. Вид: плоский (≤ 15°), наклонный, неизвестный. **Без подтверждения считается только** плоское стекло с «зенит/skylight/roof light/фонар» в имени; остальные типы — «уточните тип фонаря» (кнопки по типу: шахтный/зенитный Б.3 или не считать), до решения помещение получает статус «уточните». H — потолок рядом с фонарём, hш — от потолка до стекла. Над фонарём непрозрачная конструкция — фонарь не учитывается (пояснение); препятствия выше 45° с 2+ сторон — предупреждение. Допущения (шахта вертикальная, ρ стенок 0,7, τ1/τ2 — настройки, τ3 = τ4 = 1) показываются в карточке; в карточке — таблица фонарей и вклад каждого в каждой точке (прямой coef·qc·τ0·MF·CN + доля отражённой). **Модель 1226 (09.10.2026):** фонари — 64 экземпляра семейства A_GMO_Skywindow_Angle (категория «Окна», размещены на уровне L02_Roof, 8 типов «D1-…_D2-…_H…»).
