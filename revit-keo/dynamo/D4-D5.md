# Реальные входы и серый диагностический план

Эксперимент по [ТЗ v0.3.5, разделам 3–5/7–8](../../tasks/KEO_REVIT.md), существующие Issue #13 / PR #15. **D4 и D5 в целом не завершены.** Получены предварительные численные сценарии по кандидатам из модели и полное совпадение их JSON с независимой загрузкой исходников калькулятора. Это не подтверждение входов или нормативного соответствия; окончательной марки КЕО ещё нет.

## Что проверено в Revit

24.10.2026, прежняя standalone копия, Revit 27.3.0.28 / Dynamo 4.2.1.5887 / PythonNet3. Два чтения D4 дали одинаковый payload и неизменённое состояние документа; False проверен до/после. Группа светового климата подтверждена автором и сохранена в приватных настройках проекта, не в алгоритме.

Проверка выбранного Room обнаружила внутреннее окно и две открывающиеся створки витражей. Их Width/Height не описывают полный наружный световой проём. Один host криволинейный. Старый АР2 относится к другой версии планировки: совпадающий номер Room обозначает другое помещение. Его размеры/точка/численный результат не перенесены. Отображаемый нулевой VisibleLightTransmittance также не принят как физический коэффициент пропускания.

Для этого Room выполнен отдельный **серый диагностический D5**, по поручению автора перейти к подсветке/марке на той же копии. После preview и проверенного отката записаны один новый текстовый shared-параметр статуса, его значение только у выбранного Room, один независимый план, серая цветовая схема, существующая нативная RoomTag и отдельная TextNote с причиной. Значения КЕО/нормы не записывались. На открытом плане визуально подтверждены серая заливка, номер/название и читаемая причина. Это не приёмка зелёного/красного статуса или окончательного семейства марки КЕО.

Файлы исходного и тестового RVT имеют прежние SHA-256; сохранений/новых RVT нет. После apply `IsModified=true` ожидаем: результат находится в открытом сеансе. Граф оставлен Manual/False, отмена после apply проверена. Не сохранять/закрывать модель автоматически для обхода guard. Чистый D0–D4 guard после записи намеренно откажет; продолжение чтения требует отдельно проверенного текущего состояния, а не подмены `IsModified`.

## Файлы и запуск

- `d4_inputs.py`, `build-inputs.cjs`, `KEO_D4_InputCandidates.dyn`, `config.inputs.example.json` — диагностическое чтение. Это не готовый production adapter: исследовательский захват включает общий список Rooms/окон и ресурсов марки для выбора первого профиля. Он не становится обязательным полным обходом для каждого расчёта. Метаданные окон сохраняются по фазе; полные параметры читаются у окон, связанных с выбранным Room. Никакой параметр автоматически не становится подтверждённым расчётным входом.
- `d5_pending.py`, `build-pending.cjs`, `KEO_D5_PendingPlan.dyn`, `config.pending.example.json` — только PENDING, без численных результатов и сохранения RVT. Три входа: локальная конфигурация, Boolean, nonce. Графы поставляются Manual / False / пустой путь, с разными ID.
- `create-status-definition.py` — создаёт отдельный файл определения shared-параметра в **UTF-16LE с BOM**; существующий файл не перезаписывает. Кодировка проверена в реальном Revit: UTF-8 привёл к отсутствию кириллического определения. Настройка `SharedParametersFilename` временно переключается и восстанавливается в `finally`.
- `test_pending_plan.py` — 12 проверок отказов/идентичности, отсутствия численного результата и свежего перечитывания. Вместе с прежними D0–D2: **61 Python-тест (включая 7 проверок профиля)**.

1. Заполнить локальный `config.inputs.example.json`: прежний guard путь/хеш/build, Room UID и Phase UID, отдельный `.jsonl`. D4 должен дважды вернуть `INPUT_CANDIDATES_CAPTURED`, одинаковый `payloadSha256`, `documentUnchanged=true`. False — отмена до чтения Revit. Один успешный объект журнала сохранить локально как `.json` для preview; не включать частные данные в Git.
2. Подготовить новый локальный `.txt` командой `python create-status-definition.py <absolute-new-path.txt>`. В конфигурации D5 указать evidence, Room, UID существующего плана того же уровня, UID типа RoomTag и текста, имя нового плана и конкретную причину. Не использовать номер/семейство/этаж тестовой модели как правило отбора.
3. `action=preview`, True и новый nonce: получить список изменений и `planSha256`. Проверить цель/причину/марку и полномочия на запись. Сам хеш означает совпадение preview, **не** разрешение пользователя.
4. С тем же планом указать `approved_plan_sha256`, сначала `action=rollback`. Требуется `ROLLBACK_VERIFIED`, `inputPayloadUnchanged=true`. После отката Revit может менять внутренний VersionGUID. Такой случай принимается только при неизменности остальных snapshot-полей и полном повторном чтении/совпадении payload; остальные расхождения дают отказ.
5. Только после успешной репетиции и разрешения на конкретную тестовую копию — `action=apply`, новый nonce. `PENDING_PLAN_APPLIED` возвращает созданные UID. Открыть созданный план в Revit и проверить видимость заливки/размещение марки/причину. Вернуть False и выполнить отмену. Сохранение RVT не выполняется.

Предпросмотр проверяет чистое сохранённое состояние и конфликт существующего GUID/имени параметра, имени плана и схемы; отказ не разрешает перезаписывать существующее. Транзакция и группа откатываются при исключении до завершения группы. Повторный apply не является обновлением: после первой записи dirty guard отказывает, в чистом документе с конфликтующим объектом также будет отказ. Не удалять пользовательские объекты ради повторного теста.

D4 bundle `1599e2100ae81d4aeca6e6325a74b4527a9e88a10837cfe2bbd59dab3d41b235`; D5 bundle `138c9979397381dbe4bf460ffeb5f63c114b8fe03142829777a49bfc0413dd4c`. Исправлены чтение имени FamilySymbol в PythonNet3 и ширина TextNote: это бумажные футы, не модельная ширина.

Диагностический D5 пока не готов для массового использования: строгая ограниченная схема/лимиты его журнала и запись всех ошибок, обновление/удаление собственных артефактов, проверка cancel во время транзакции, все типы фаз/вариантов/планов, размещение без коллизий, автоматический stale, спецификация и семейство КЕО ещё открыты. Использованный RoomTag может отображать дополнительные стандартные поля; он не объявляется итоговым оформлением. Подпись причины статическая; при изменении входов её актуальность автоматически не отслеживается.

Следующее: первый поддерживаемый профиль с подтверждёнными активными полями, без принудительного выпрямления криволинейного фасада. Требуются применимость расчётной схемы и точки, полный набор используемых проёмов/обмер, сопоставление назначению справочника, используемые коэффициенты и затенение. Это конкретные входы калькулятора, не требование исследовать всю сцену/материалы. После этого — неизменённый runner, реальный экспорт/сверка и численная марка; диагностический план не закрывает эти задачи.


## Уточнение назначения, профиль и АР3 — 24.10.2026

Перед геометрическим сбором определить нормативное назначение: подтверждённая норма → нужные поля выбранной схемы; подтверждённое отсутствие нормы → EXCLUDED/серый «КЕО не нормируется» со ссылкой на строку; неизвестное назначение → PENDING. Отсутствие строки в оцифрованном справочнике само по себе не означает отсутствие нормы. Не назначать переговорной норму рабочего кабинета только по принадлежности к административному блоку. Функция рабочего места, включая специальное оборудование, может требовать иной строки; неоднозначность сохранять явно.

Текущая Revit-модель является источником состава и геометрии помещений. Невыпущенный обновлённый АР2 не является зависимостью расчёта. АР2/АР3 проекта используются для проверки подхода подрядчика, схемы и происхождения коэффициентов; старые размеры, номера, результаты и переход на СО автоматически не переносятся. Во время тестов по каждому выбранному назначению проверять нормы в сети и по экземплярам на Google Диске, фиксируя документ, редакцию, пункт/строку и дату проверки. Это проверка при разработке; пользовательский runtime остаётся локальным.

[Нормативные строки, критерии и источники](NORMS.md) проверены в сети и по исходным СП на Диске. Кандидат с функцией переговорной не принят как рабочий кабинет: его прежний пробный численный результат не становится нормативным. Для административного кабинета с верхним светом выполнен отдельный предварительный прогон по пяти точкам; полный результат совпал с независимой загрузкой калькулятора и повторным импортом state v:1. JSON-интерфейс калькулятора проверен программно; ручное открытие этого JSON в браузерной форме ещё не проверено. Эквивалентная схема ступенчатого фонаря и затенение ещё проверяются, цвет PENDING. Автор подтвердил расчётный набор АР3 без требования будущего изделия; нормативное происхождение значений проверено отдельно, см. NORMS.md.

`d4_profile.py`, `build-profile.cjs`, `KEO_D4_ProfileRead.dyn`, `config.profile.example.json` продолжают только чтение после точно записанного D5 apply. Проверяются документ/путь/build/хеш и полное совпадение snapshot с единственной успешной записью apply, включая ожидаемый IsModified=true. Неизвестная версия документа, иной файл или неоднозначный журнал дают отказ. Это узкий диагностический guard, не общий режим работы с любыми несохранёнными изменениями. Опциональный `detail_window_uids` ограничен тремя явно выбранными уже захваченными окнами; физическая геометрия читается только для них. Здесь она понадобилась для высоты светового канала, которую не описал параметр семейства. Локальные кандидаты затенения не доказывают полноту окружения.

В Revit проверены профиль помещения, повтор одного профиля и целевой захват одного фонаря; documentUnchanged=true. Последний bundle `8fc33ac0eb92b331193d991189cd9b0ca68415a27d39daab2cc8aa58db6be063`. False после чтения вернул CANCELLED. Два повтора каждого нового геометрического профиля пока не заявляются. Сравнение с АР3 проверяет метод подрядчика, не переносит старую планировку/значения.

После завершения чтения собственная TextNote на существующем сером плане уточнена через Revit UI: удалена фраза об устаревшем АР2, сохранена конкретная причина по схеме витража/полноте проёмов. Визуально проверено, новых видов/марок не создано. Случайно открытый режим эскиза перекрытия отменён без правок; напоминание о сохранении закрыто без сохранения. После правки текста прежний snapshot профиля устарел: дальнейшее чтение требует проверки нового текущего состояния, не обхода guard.

Уточнение автора о нормативных проектных коэффициентах включено в ТЗ v0.3.3. Паспорта будущего стеклопакета и заполненные оптические свойства Revit не являются обязательными входами. Проверенные нормативные значения, выбор расчётной категории и проектные допущения имеют разные подписи происхождения.


## Согласованный проём и предварительный численный план

24.10.2026, ТЗ v0.3.4. Предыдущий несохранённый D5-сеанс был закрыт; его объекты не считались сохранившимися. Повторно открыта та же standalone RVT с прежним хешем. Отдельное открытие сохранённого `KEO_D4_ProfileRead.dyn` теперь проверено; пользователь самостоятельно ответил на запросы конфиденциальности и открытия внешнего файла. Player по-прежнему не проверен.

Профиль поддерживает явный `baseline_mode=clean-file` с полным D0 guard либо прежний `recorded-apply` (значение по умолчанию). Режимы нельзя смешивать. Необязательный `section_probe` читает только явно выбранные захваченные кандидаты: 1–8 элементов, 1–48 конечных отрезков, до 16 точек Room; все координаты — метры в внутренних осях корневого Revit-документа. Геометрия символа проходит через накопленный transform, ошибки не превращаются в пустой результат. Эти пробы не являются решателем КЕО или доказательством видимости всего неба.

В Revit дважды получен одинаковый профиль с 7 выбранными элементами, 22 отрезками и 5 точками; все точки внутри Room. Установлено сплошное потолочное перекрытие под световым каналом. Автор подтвердил, что сквозной круглый проём предусмотрен проектом, и отдельно разрешил вырез на этой тестовой копии. Точные размеры/координаты/UID сохранены приватно.

Новый `d5_approved_opening.py` — узкий эксперимент, запускаемый только по явному разрешению для конкретного тестового исправления. Он не входит в обычный автоматический расчёт Rooms. `build-approved-opening.cjs` собирает `KEO_D5_ApprovedOpening.dyn`: Manual/False, пустой путь. Конфигурация содержит guard, исходный PROFILE_CAPTURED, встроенную конфигурацию повторного профиля, исходный runner result и его SHA-256, единственный host/центр/диаметр/диапазон высот, запись разрешения, ресурсы отдельного плана и причину PENDING. Исходный результат проверяется по Room UID и fingerprint; числа берутся из runner JSON, формулы в Python не реализованы. Пример структуры — `config.approved-opening.example.json`.

Порядок: `preview` → проверка плана и его хеша → `rollback` с тем же хешем → только после успешного отката `apply`. Оба действия (серый план и проём) объединены общей TransactionGroup; при ошибке до Assimilate всё откатывается. Один вертикальный Opening создаётся в явно выбранном Floor через штатный NewOpening. Проверка: ось и 8 точек внутри окружности освобождены; 8 точек непосредственно снаружи сохраняют толщину host. После rollback повторно совпали профиль, контрольные сечения и snapshot; IsModified=false. После apply повторно прочитаны сечения и численный текст, IsModified=true. Повторный запуск не размножает объекты: dirty guard/конфликты отказывают; безопасное обновление своих объектов ещё не реализовано.

Фактически выполнен bundle `7506d0d147115fb7d07f9ef44c9d859f858ef6f59cdeaf4d65ada929e9b7f6d8` в открытом трёхвходовом D4-каркасе. Отдельное открытие нового D5 .dyn не заявляется. UI целочисленного поля не всегда обновлял значение slider; фактические nonce брались из возвращённого результата, повтор гарантирован проверенным циклом False/Run → True/Run. После apply проверен CANCELLED; граф оставлен Manual/False.

Предварительный state импортирован через «Открыть» в локальную браузерную форму неизменённого standalone-калькулятора (HTML SHA-256 `ee11ec7a72944fc8069bfa9d7a0fb70fd0faa0dc6447531c889164f1d7752e94`). Норма, среднее и пять значений совпали с runner; это дополнение к прежней программной сверке, не нормативная приёмка. Неоднозначность ступенчатого верха шахты и нужного затенения остаётся. τ1/τ2 имеют проектный, а не автоматически нормативный статус, см. [аудит](NORMS.md).

На отдельном плане визуально проверены серая заливка, штатная RoomTag и отдельная подпись с предварительным числом, нормой и причиной. RoomTag пока содержит стандартные поля семейства, включая ненужный объём; отдельная TextNote не заменяет окончательную связанную численную марку. Размещение без коллизий, численные shared-параметры, массовое обновление, stale и спецификация остаются D5.

По отдельному ответу автора «Сохранить эту тестовую RVT» результат один раз сохранён в том же файле. Новый тестовый SHA-256 записан приватно, исходный RVT сохранил прежний хеш. Новых тестовых моделей нет; автоматически созданный при сохранении резервный .0001 удалён только после сверки с предшествующим baseline. Разрешение на будущие сохранения не подразумевается. Старые captures и guard с прежним хешем не считать актуальными; дальнейшее чтение — новый clean-file профиль сохранённого состояния.

Проверки: 73 Python-теста (10 profile, 4 section, 5 approved-opening и прежние наборы), синхронные генераторы profile/pending/approved-opening. В тестах отказ при неверной геометрии/отсутствии разрешения, пропущенном или чрезмерном вырезе, другом Room/ошибке runner; False не читает файл и не обращается к Revit. Нативный вырез и полный rollback проверены отдельно в Revit. Приватные RVT, геометрия, конфигурации, screenshots и журналы в Git не включены.

Для последних 399 элементов вернули геометрию без положительных Solid/Mesh, один контур — без геометрии. Камеры/материалы/служебные типы исключены по API-классу/категории, а не имени. Нельзя считать элементы с именем «проём» пустотами без проверки тела.
- Внешних Revit-связей нет; плоские CAD-импорты не доказывают полноту окружающей застройки. Обзор возвращает консервативные кандидаты/угловые границы, а не `shadingAccepted`. Автор отдельно подтвердил отсутствие внешнего затенения как проектное допущение этого теста. Оно не означает доказанную полноту модели и не отменяет проверку объектов на кровле.
- По просьбе автора создан один диагностический разрез и показан увеличенный фонарь. После просмотра автор уточнил: семейство условное, расчётные отверстия и стекло определяются параметрами. Оба диаметра проверены в прежнем API-захвате и в Type Properties; проектные GUID/значения находятся только в приватной конфигурации. Наружная геометрия стекла не является расчётным размером. Радиус и диаметр не смешаны. Это решение устраняет прежнюю гипотезу о расчёте промежуточной ступени данного условного семейства; для произвольных реальных ступенчатых шахт принятие не распространяется.
- После создания разреза появились несохранённые изменения вида. RVT не сохранялась, новый clean-file baseline для открытого документа не заявляется. Не сбрасывать изменения и не обходить guard.

### Adapter параметров — офлайн на захвате

`parameter_dimensions.py` принимает уже прочитанные instance/type параметры и отдельное сопоставление. Для каждого поля — ровно один GUID/ID/однозначное имя, явный scope, смысл и основание. Проверяются Double/HasValue/Length/положительное конечное значение; внутренние футы переводятся в метры, радиус — в диаметр. Верхнее и нижнее отверстия обязательны и независимы; `hsf` опционально с семантикой длины. Результат сохраняет происхождение и сам не выдаёт geometryAccepted.

Импорт модуля: `from parameter_dimensions import shaft_dimensions`; вызов `shaft_dimensions(captured_window, mappings)`, где `mappings` содержит `dv`, `dn` (и при наличии `hsf`), каждое с `scope`, одним из `guid/id/name`, `quantity` (`diameter/radius/length`) и `basis`. Отсутствующее поле вызывает диагностическую ошибку; значения/aliases по имени семейства не подставляются. Это самостоятельный шаг на захвате, ещё не новый пользовательский граф/Player.

7 новых проверок: единицы/радиус, instance/type, иные имена/регистронезависимый GUID, пустые/дублирующие значения, неверная размерность/nonfinite, обязательный смысл/основание и независимые разные отверстия. Весь набор — **86 Python-тестов**, генератор shaft --check совпадает. Испытание с синтетическими переименованиями не заменяет D6 на другой модели.

### Осталось

Повторный расчёт исходным JS-ядром по выбранным параметрам выполнен; полный результат совпал с независимой загрузкой пяти исходных модулей калькулятора. Проверены среднее, норма и пять точек отдельно от принятия окружения. Хеши исходного и тестового RVT на диске совпали с контрольными. Прежняя проверка браузерного импорта сохраняется для совпадающего численного набора, но новый UI-импорт не заявляется. Отсутствие внешнего затенения принято автором для этого теста; влияние объектов на кровле и итоговый допуск ещё не приняты. Вид будущей трёхстрочной RoomTag согласован автором; связанная численная марка пока не создана. Старые серые RoomTag/TextNote остаются диагностическим результатом. D4/D5 целиком не закрыты.
