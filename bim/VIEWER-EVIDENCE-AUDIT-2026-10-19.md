## Цикл 1: площадь не удостоверяет Room

Гипотеза подтверждена чтением кода и синтетическим воспроизведением: взаимно
единственная пара по площади/периметру могла получить `rm.reg`; единственная
сумма площадей могла получить `byBalance`. Ни один путь не проверял положение
Room. Из этого следовала возможность расчёта чужого контура под именем Room.

Исправление ограничено runtime: `requireSpatial:true` оставляет геометрию и
индивидуальные кандидаты в диагностике, но не назначает их Rooms. Баланс площадей
не назначает Room и не запускает перебор сочетаний 2–3 Rooms. Историческая
эвристика остаётся в модуле для изолированных сравнительных тестов; пользовательский
runtime её не включает и не предлагает переключатель для обхода ограничения.
Подтверждённый автоматический источник положения пока отсутствует. Следовательно,
**в этой ветке все автоматические привязки Rooms приостановлены**. Это не готовая
реализация универсального сопоставления и не улучшение точности измеренных границ.

Ручной выбор требует самостоятельной проверки положения, этажа и принадлежности
модели/связи. Он обозначается как ручной, действует только в текущем полном
анализе и на указанном уровне. Старые записи остаются в данных, но не используются
как пространственное основание при новом анализе. Неподтверждённые границы и КЕО
от этого не становятся достоверными. Совпадение XY разных этажей не удаляет ручное
решение другого этажа. Повторяющиеся ключи Rooms блокируют обработку, вместо
потери одного из объектов при создании Map. Устойчивый составной ключ для связей
ещё предстоит реализовать; `dbId` и голый `ElementId` им не объявляются.

Проверки охватывают единственный подходящий контур, удалённый кандидат, сумму
площадей, устаревшие метки, повторяющиеся ключи, явный ручной выбор, старый сеанс и
другой уровень. На реальном коде панели проверено: без ручного размещения ни один
вызов расчёта пространства не выполняется; подтверждение назначения здания не
обходит отказ геометрии. В таблице показывается отсутствие подтверждения, не
числовой ноль КЕО. Показывается время полного анализа.

## Цикл 2: загрузчик кнопки

Прежний href не проверял HTTP-статус, запускал `KeoBim.run()` после любого тела
ответа, не ожидал его Promise и не защищал порядок параллельных загрузок.
Комментарий/пустой файл мог оставить старый объект приложения; запоздавший ответ
мог заменить новую версию старой. Это воспроизводимые дефекты загрузчика,
**не установленная причина прежнего нуля Rooms на живой модели**.

Новый href генерируется из `bim/bookmarklet.js`; fetch требует успешный HTTP,
после исполнения должен появиться новый объект приложения, run ожидается.
Последнее нажатие отменяет предыдущую загрузку; завершение старого ответа или
его тела не запускает приложение. Проверяется сам href из сборки, включая чистую
VM, повтор, отказ сети/HTTP, неверный файл, async-ошибку и обе гонки ответов.
Реальная сборка отдельно инициализируется без заранее созданных KeoBim/KeoBimLib;
Autodesk SDK в этом тесте обозначен минимальным mock. **VM не проверяет CSP,
установку закладки пользователем, браузерные разрешения и загрузку модели.**

Сборка останавливается при ошибке команды (`set -eu`), а не продолжает молча
копировать неполный результат. Старые уже установленные закладки имеют прежний
href: после возможного выпуска для исправлений загрузчика потребуется установить
кнопку заново. Runtime по прежнему публичному URL сохраняется совместимым.

## Проверка формулы и границы точности

Формулы, таблицы норм и коэффициенты в этом изменении не редактировались.
Четыре команды сверки выполнены в изолированной базовой ревизии и кандидате;
stdout побайтно одинаков, коды завершения 0:

- `node bim/verify-side.js`
- `node bim/verify-side.js bim/verify/1226-L01.json`
- `node bim/verify-top.js`
- `node verify-danilyuk.js`

Это доказательство отсутствия изменения этих численных входов. Оно не доказывает
правильность извлечения новых помещений. Независимое интегрирование в имеющихся
контролях по-прежнему отличается от нормативной аппроксимации; сравнение Данилюка
содержит ранее документированные расхождения. Эти расхождения не скрыты и не
исправлялись подбором коэффициентов. Указанный в инструкции проекта допуск для
контрольных примеров нельзя переносить на точность всей цепочки Viewer → Room →
окна → расчёт. Для всей цепочки подтверждённого допуска пока нет.

из проверки равенства бизнес-решений; их смена/отказ старой привязки проверяются
отдельно.

## Что говорят первичные источники Autodesk

Проверены 19.10.2026:

- [Master views и Rooms в SVF2](https://aps.autodesk.com/en/docs/model-derivative/v2/tutorials/prep-roominfo4viewer): Autodesk документирует дополнительный вид по стадиям с элементами Rooms. Поэтому категорическое «Viewer не содержит геометрии Rooms» удалено из инструкции.
- [Composite Revit translation, 04.06.2025](https://aps.autodesk.com/blog/translate-composite-revit-model-model-derivative-api): в описанном Autodesk сценарии связанные элементы присутствуют в обычных видах, но отсутствуют в master views. Само наличие master view не доказывает полноту внешнего затенения.
- [getExternalIdMapping](https://aps.autodesk.com/blog/get-dbid-externalid): штатное отображение externalId → dbId позволяет работать с идентификатором источника. Для привязки нескольких экземпляров связей всё равно нужны контекст источника/экземпляра и преобразования.

Это направления следующего исследования, не результаты проверки конкретного
экспорта viewer.autodesk.com. Перевод модели через APS здесь не запускался;
его доступность в обычной загрузке Autodesk Viewer не установлена. IFC не
вводится как обязательное условие. На основании этих материалов не назначен
новый регламент подготовки RVT.
